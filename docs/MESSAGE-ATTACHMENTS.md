# 消息文件附件

输入框和编辑重发支持选择文件，以及粘贴 WebView 剪贴板实际提供的 File。
每条消息合计最多 4 个附件（包括图片），前端与 Runtime 同时校验；旧客户端
`imageAssetIds` 保持兼容，新客户端使用 `attachmentAssetIds`，两组 ID 共用额度。
从系统文件管理器复制文件时，三个平台的剪贴板格式不同，不能保证都会转成
WebView File；文件选择器是统一入口。跨平台剪贴板与界面仍需真机验收。

## 范围

- PNG/JPEG/WebP/GIF 沿用视觉输入，每张最多 4 MiB。
- UTF-8 文本/代码白名单保留文件名、原始行号，不执行代码。
- PDF 保留页码，最多 200 页；任一页无可提取文字即明确拒绝并提示需要 OCR。
- DOCX 提取正文段落与表格文字、保持正文顺序；不还原样式、图片、页眉页脚。
  旧 DOC、扫描件、加密/损坏文件不支持，不读取外部关系或运行宏。
- 每份文档原始大小最多 10 MiB、提取结果最多 60000 字符（含行号/页码）。
  每条消息文档提取结果合计最多 120000 字符；超限拒绝，不静默截断。

## 数据与上下文

`contracts` 定义上传协议和 `file` 内容块；前端只经 runtime-client / API 调用。
文件字节经用户明确选择的 File 上传到会话 Asset Store，不以用户提供路径读取
磁盘文件。拒绝凭据类文件名和路径型文件名。原文件 hash、格式、大小与提取结果
存入 Asset 元数据，消息 `file` 块保存提取快照；消息正文仍为用户输入文字。

Runtime 按 canonical 内容块将提取文字投影至模型上下文，标注文件名、参考材料
边界和不可信属性，计入现有上下文预算与压缩机制。附件文字不获得指令或工具授权。
PDF/Word 无需 Provider 专有文件 API，三种现有 Provider 共用文本路径。
图片仍需模型支持视觉；文档只提供文字，无法理解嵌入图片和视觉排版。

PDF/DOCX 使用有界 Worker：最多并发 2 个、每个 15 秒、256 MiB V8 heap，
完成/失败/超时后终止线程；DOCX 限制 ZIP 条目数与解压大小，拒绝 DTD/实体声明。
解析日志不进入 stdout 协议或用户错误；不增加常驻心跳、线程或订阅。
macOS、Windows、Linux 使用同一 Node 实现，不依赖本机 Office、Python 或系统命令。
开发态由 tsc 输出 Worker，安装包额外打包 `document-worker.mjs`，与 runtime.mjs 同目录。

编辑重发支持保留、移除和替换附件；重试、重启后的已发送消息从持久化块恢复。
现有发送队列仍为内存队列，重启不会恢复排队项；附件功能不改变该语义。
消息/队列引用的资产禁止直接删除。聊天备份保存原始文件，导入时重新校验和解析，
重建当前会话资产引用；包含文档的备份使用 v2；旧版 v1 备份仍可导入，备份总上限仍为 16 MiB。
